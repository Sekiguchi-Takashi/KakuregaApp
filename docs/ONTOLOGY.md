# カクレガ 錠オントロジー v0.1

「色々なパターンで守られる」を型の列挙で実現すると、パターンを足すたびに設計が壊れる。錠を要素に分解し、合成規則を定義すれば、パターンは無限に作れて診断も一本化できる。BunsanAppで「安全性を決めるのは k/n でなく配置だった」のと同型の発見がここにもある: **錠の強さを決めるのは錠の種類ではなく、秘密がどこに住んでいるか**。

---

## 1. 実体

| 実体 | 定義 |
|---|---|
| 守衛対象 | スロットの中身（保管ファイル群） |
| 解錠要素 | 錠を構成する最小単位。単独または合成されて錠になる |
| 錠 | 解錠要素の条件式（AND/ORの木）。スロットに1つ付く |
| 秘密の所在 | 各解錠要素の秘密が物理的に存在する場所（§3） |
| 攻撃者クラス | 想定する敵の能力段階（§4） |
| 復旧経路 | 要素を失ったとき中身に到達する代替経路（ORの枝） |

## 2. 解錠要素の分類

| 要素 | 認証学上の因子 | 秘密の所在 |
|---|---|---|
| 隠し場所（見えないホットスポット） | 知識（在処） | 同一端末DB内 |
| 鍵アイテム | 知識（鍵の在処＝ゲーム進行） | 同一端末DB内 |
| PIN | 知識（頭の中） | 利用者の記憶（端末にはハッシュのみ） |
| 分散片 | 所持（片ファイル） | 別ファイル（配置先次第で端末外） |
| LANペア | 所持（第二端末）＋近接（同一Wi-Fi） | 別端末 |
| 受託者ペア（家族の端末） | 所持＋他者の同意 | 別人の端末 |

**重要な発見**: 鍵アイテムは直感的には「所持」だが、オントロジー上は「知識」である。鍵の在処も入手済みフラグも同一端末のDBに書かれているため、DBを読める攻撃者には存在しないのと同じ。つまり錠には2階層ある:

- **演出としての錠** — 隠し場所・鍵アイテム。ゲーム体験と、端末を一時的に触る人への防御
- **実効的な錠** — 秘密が端末の外にあるもの。分散片・LANペア・受託者ペア（PINは中間: 記憶にあるが、ハッシュが端末内にあるためオフライン総当たりに弱い）

## 3. 秘密の所在（5段階）

1. 同一端末DB内 — 隠し場所、鍵アイテム
2. 利用者の記憶 — PIN
3. 別ファイル — 分散片（ただし片を同じ端末に置いたら①に堕ちる。所在が強さを決める）
4. 別端末（自分の） — LANペア
5. 別端末（他人の） — 受託者ペア

番号が大きいほど端末解析に強く、同時に喪失リスクも上がる。BunsanAppの独立性グループの概念がそのまま輸入できる: ③④⑤が同じ部屋の同じ棚にあるなら、それは①と大差ない。

## 4. 攻撃者クラス

| クラス | 能力 | 破れる所在 |
|---|---|---|
| A1 覗き見 | アプリを開いて画面を触れる | なし（隠し場所すら総当たりが要る） |
| A2 端末占有 | 時間をかけて操作できる | ①（総当たり探索）、②（PIN試行、バックオフで遅延のみ） |
| A3 端末解析 | root/adbでDBとvaultを直読 | ①②（ハッシュ総当たり含む） |
| A4 家庭内共犯 | 同一Wi-Fiにいて別端末も触れる | ①②③④（片や第二端末が同じ家なら） |

## 5. 合成規則と判定

錠 = 条件式。例: `(鍵アイテム AND PIN) OR (LANペア)`

- **機密性の規則**: 攻撃者クラスAに対して安全 ⇔ **すべてのOR枝**に、Aが破れない所在の要素が最低1つ含まれる
- **可用性の規則**: 利用者が締め出される ⇔ **すべてのOR枝**に、失った要素が最低1つ含まれる

この2つは正確にトレードオフになる（BunsanAppの 漏洩耐性 c(g)<k / 喪失耐性 n−c(g)≥k と同じ双対）。ANDを深くすれば機密性が上がり喪失に弱くなる。OR（復旧経路）を足せば締め出しに強くなるが、最弱の枝が実効強度を決める。

- **最弱枝の原則**: `(分散片 AND LANペア) OR (PIN)` の実効強度はPIN単独と同じ。復旧経路を足すときは必ず本経路と同等以上の所在レベルにするか、意図的な格下げだと利用者に明示する

## 6. 診断エンジン（BunsanApp方式の移植）

スロットごとに純粋関数で判定し、バッジ表示:

- 入力: 錠の条件式、各要素の所在（分散片は配置先グループ、LANペアは相手端末のグループ）
- 出力: クラスA1〜A4それぞれの 防御可/不可、締め出しリスク（単一喪失で全滅する要素の列挙）、是正案
- 是正案は適用後に再診断して両立するものだけ提示（BunsanApp監査M3の教訓を継承）
- 所在が未申告の要素は UNDECIDABLE として安全側（防御不可扱い）に倒す
- 表示は正直に: 「この判定は、片や相手端末の所在申告が実態と一致している場合のもの」

## 7. UIへの落とし込み

- 錠の条件式は式エディタを見せない。プリセット名で選ばせ、内部表現だけ条件木にする:
  - 「かんたん」= 隠し場所のみ
  - 「金庫」= PIN
  - 「厳重」= 鍵アイテム AND PIN
  - 「二台金庫」= LANペア
  - 「最深部」= 分散片 AND LANペア
  - 「家族金庫」= 受託者ペア OR (PIN AND 鍵アイテム)  ※復旧経路の例
- 各プリセットに診断バッジ（A1〜A4の盾アイコン）を常時表示。「厳重」でもA3には無力であることを隠さない
- カスタム合成はPhase 3後半で開放（条件木エディタ）

## 8. 不変条件

1. 錠のシリアライズ形式（条件木JSON）はバージョン付きで旧版読取を永久維持
2. どの錠も「アプリが消滅しても中身を救える」経路を診断で確認できること（vault直コピー＋錠情報のエクスポート）。分散片だけは例外で、BunsanApp側のFORMAT_SPEC.mdが救済線
3. 秘密の平文をネットワークに流さない（LANペアはHMACチャレンジレスポンス）
4. 診断エンジンはContext/DB非依存の純粋関数とし、起動時selfTestで回帰検知（BunsanApp方式）

## 9. 検証ケース（selfTest用・初期8件）

1. 隠し場所のみ → A2以上で防御不可
2. PINのみ → A3で防御不可、喪失リスク=記憶のみ
3. 鍵AND PIN → A3で防御不可（両方とも所在①②）
4. LANペアのみ → A3防御可、A4は相手端末が同一グループなら不可
5. 分散片（片が同一端末）→ 所在①に堕ちてA3不可
6. 分散片（片が別グループ）→ A4まで防御可
7. 強経路OR PIN → 実効強度はPINに落ちる（最弱枝）
8. 所在未申告の要素を含む → UNDECIDABLE
